# PostgreSQL

Add a Postgres service for local development and tests, a migration workflow, and a test harness where every test file gets a private, fully migrated database in milliseconds. Migrations are the only source of truth for the schema. Tests build their schema by running them, never by creating tables from models.

## What to add

**Compose file** (`compose.yaml` at the root, or extend one if it exists). Write it against the current Compose spec:
- `db`: the chosen image, user/password/database from env with dev defaults (`app`/`app`/`app`), host port `${PORT_DB:-5432}`, a named volume for data, and a healthcheck running `pg_isready -U <user> -d <db>` every few seconds with a start period. Check the image's docs for the data-volume mount path; it changed in recent majors.
- `db-test`: same image, host port `${PORT_DB_TEST:-5433}`, no named volume (tmpfs for the data directory), and durability off for speed (`fsync=off`, `synchronous_commit=off`, `full_page_writes=off` as server flags). It exists only to be thrown away. Same healthcheck.

**Env** (add to `.env.example` with comments):
- `PORT_DB=5432`, `PORT_DB_TEST=5433`
- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` with dev defaults
- `DATABASE_URL` pointing at `db` on `PORT_DB`, in the driver's URL form (for SQLAlchemy async: `postgresql+asyncpg://...`)
- `TEST_DATABASE_URL` pointing at the `postgres` maintenance database on `db-test`; the harness creates databases from there

**Makefile targets** (add to the existing Makefile; verify calls the first three):
- `db-up`: `docker compose up -d db db-test`, then wait until both are healthy (Compose's wait flag, or a `pg_isready` retry loop with a timeout that fails loudly).
- `db-migrate`: apply all migrations to the dev database.
- `db-down`: `docker compose stop db db-test` (stop, don't remove, so dev data survives).
- `db-reset`: drop and recreate the dev database, then migrate.
- `db-new-migration NAME=...`: create a new migration (autogenerate from models where the tool supports it).
- `db-shell`: `psql` into the dev database through `docker compose exec`.
- `db-check`: fail if models and migrations disagree (Alembic's check command, drizzle-kit's check, or the Go equivalent). CI runs this.

**Migrations by language.**
- *Python (python-react)*: SQLAlchemy async ORM models in its typed declarative style in `backend/app/db/models.py` with a shared declarative `Base` and a naming convention for constraints (so autogenerated migration names are stable). Alembic initialized with its async template in `backend/migrations/`, `env.py` reading the URL from the app's `Settings` (never from `alembic.ini`), and `target_metadata = Base.metadata`. Create the async engine in the app's lifespan, store it on `app.state`, and expose a `get_session` dependency yielding an `AsyncSession` per request. Add `database_url` to `Settings`.
- *TypeScript*: drizzle schema in `src/db/schema.ts`, drizzle-kit config reading `DATABASE_URL`, generated SQL migrations committed under `drizzle/`, applied with drizzle's migrator.
- *Go*: pgx pool created once in main and passed down; goose SQL migrations in `migrations/`, applied by `make db-migrate` and embeddable with `embed.FS` for release builds.

**Health.** Keep `/health` DB-free (liveness). Add `/health/ready` that runs `SELECT 1` and returns 503 with the error envelope if the database is unreachable.

## Test harness

This is the part worth getting right; it makes DB tests fast, isolated, and parallel-safe.

1. **Template, once per run.** At session start, connect to the maintenance database from `TEST_DATABASE_URL`, take a Postgres advisory lock (a fixed arbitrary integer) so concurrent runs and parallel workers serialize, drop leftover test databases from crashed runs (by name prefix), drop and recreate `<project>_template`, release the lock, then run the real migrations against the template and close every connection to it. Rebuilding every run means a schema change can never be served from a stale template.
2. **One database per test file.** Each test file (Python: module-scoped fixture; bun/vitest: a `beforeAll` helper) runs `CREATE DATABASE "<prefix>_<label>_<random>" TEMPLATE "<project>_template"`. That's a file copy: fast, and already migrated. Point the app's database URL at it, then build the app.
3. **Teardown.** After the file, close pools and sessions, then `DROP DATABASE ... WITH (FORCE)`.
4. **Within a file**, tests share the database. Either make each test create its own rows with unique ids, or wrap each test in a transaction that's rolled back, whichever fits the ORM. Don't truncate everything between tests; it's slow and hides ordering bugs.
5. **Parallel runners** (pytest-xdist, bun, vitest workers) need nothing extra: the lock guards the template build, and per-file names are random.

Expose it as one call per test file (for example `db = setup_test_database("users")` in Python, `const t = setupDbTest("users")` in TS) so test files state what they need and nothing else. `CREATE DATABASE ... TEMPLATE` fails while anything is connected to the template, so the template build must close its connections before the first clone. Raise the test framework's hook timeout if the default is only a few seconds; the first file pays for the template build.

If the user chose testcontainers instead of the compose test service, start one container per test session and apply the same template-and-clone steps inside it.

## CI

Add a Postgres service container to the job that runs the backend tests (same image, healthcheck options, `TEST_DATABASE_URL` pointed at it), and run `make db-check` before the tests so a model change without a migration fails in CI.

## Verify

`db-up` and `db-migrate` run in setup, after the stack's install step, so the database is up and migrated before tests. `db-down` runs in teardown and always runs, even when earlier steps fail.
