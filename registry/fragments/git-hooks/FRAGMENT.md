# Git hooks (lefthook)

Write `lefthook.yml` at the repo root. Nothing is copied, because the commands differ per stack and lefthook's config schema has changed between major versions. Check the installed version's docs for the current key names (for example, whether hooks list `jobs` or `commands`) and let `lefthook validate` confirm the result.

## What to add

**Install lefthook** so the bare `lefthook` command is on PATH, since verify calls it directly: the platform package manager, the Go toolchain, or a global package install all work. It may also be a project dev dependency (the npm package, or the ecosystem's equivalent) so contributors get it with the rest of the toolchain; if so, make the install step also install the hooks. Record in `AGENTS.md` how a new contributor gets it.

**pre-commit: fast checks on staged files only.**
- One job per language area, each restricted by a glob (and a root directory in a monorepo) and passed only the staged files.
- Formatting first, with fixes re-staged automatically (lefthook's stage-fixed option), then linting in check mode.
- Call the same tools with the same config the project's `format` and `lint` commands use. Where a tool can only run on the whole project (for example golangci-lint, which needs package context), call the project's command instead of the tool.
- Run jobs in parallel when they don't touch the same files. Keep the whole hook to a few seconds; anything slower (typecheck of the whole project, tests) belongs in pre-push or CI.
- Guard optional tools (`command -v tool` before calling it) only for tools the project doesn't require. A required tool that's missing should fail the hook.

**commit-msg: Conventional Commits.** Read the message file lefthook passes to the hook and require `type(optional-scope)!?: description`, with types `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Let merge commits, reverts generated by git, and `fixup!`/`squash!` commits through. On failure, print the expected format and two examples. A few lines of shell in the config is enough; don't add a Node-based commitlint toolchain to a non-JS project.

**pre-push: the project's test command** (and lint, if the pre-commit job doesn't cover the whole project), called through the Makefile or package script, never re-implemented inline. Run them in parallel if they're independent.

Before finishing, prove the jobs actually execute: run the pre-commit hook against all files once (lefthook's `run` command has an option for this), and pipe a bad message and a good one through the commit-msg check (lefthook passes the message file path as the hook's argument) to see one rejected and one accepted.

## AGENTS.md

Add a **Git hooks** section: what runs on pre-commit, commit-msg, and pre-push; the commit message format with an example; how to install the hooks (`lefthook install`, or automatically through the install command); and that hooks must not be bypassed with `--no-verify`. If a hook fails, fix the cause; if a hook is wrong, fix the hook in the same change.
